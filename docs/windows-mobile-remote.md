# Windows mobile remote

The Windows app now hosts the same encrypted relay v1 and `/m1` protocol as the macOS app (`docs/relay.md`, `docs/mobile-remote.md`). Enable **Settings → Mobile remote**, apply a relay address, then scan the pairing QR or copy the pairing link into the phone app. The default relay is the same as macOS. No inbound PC port is opened.

The Windows host supports state and transcript history, queued or steering submissions, one-call tool approvals, questionnaires, Claude plan approvals (`plan` in the permission, `POST …/plan`), pane creation/rename/close, model/permission/effort settings, approved guided styles, commands, chunked attachments, workspace file browsing, and the phone's structure view (capability `structure`: the host's own structure view of a pane, sent only to a phone that asks and only when it changed, as on the Mac). Terminal and browser panes remain desktop-only for execution. A capability is advertised only when its routing is installed; screen sharing additionally requires the Windows capture/WebRTC engine.

What a phone is sent follows the Mac host rule for rule (`native/macos/Sources/MightyCore/Remote/`), and each rule lives in Core where the checks read it:

- **Session reply.** `mighty.runs` is the newest 20 requests with the Mac's blocks: status mapped to the phone's five words, `output` capped at 2,000 characters, `result` at 20,000 and only on the newest settled run, `durationMs` for a settled block, `activity` (its newest eight steps) for one still in motion, and `title` from the running style. A pane without a saved graph has its requests grouped from the transcript. A pending request travels with the desktop card's own title, headline and fields. An `image` transcript entry reaches the phone as its `system` line without picture references, because the phone's contract has no pictures. A pane running the bundled Ouroboros style also carries `mighty.ouroboros` for older phone apps (`mighty.paperthin` is gone: the Paperthin style was removed in v7).
- **Settings.** `options.styles` is `cli` plus the styles that can run, offered only to a Claude pane in the Mighty view (elsewhere `cli` alone). `styleId` is the style the pane is really running, so a pane in the plain view says `cli` whatever it has stored, and a phone handing that value back while it turns the Mighty view on leaves the stored style alone. `efforts` (and `effort`) are absent when the provider has no effort setting. Labels are the composer's.
- **Revisions.** Each pane has its own revision, read from a fingerprint of what the phone shows of it (its status, title, model, settings, the tail of its transcript, the settings options and the Mighty payload's identity, never the status line and never a block's streamed text). The state revision moves only when a pane's summary, the pane order or a workspace changed. A long poll waits on its own scope and a connected phone is sent `notify` only for the scopes that moved. The panes are read again four times a second while a phone is connected.
- **Style buttons.** `POST …/guided` builds the action's prompt and sends it down the ordinary send path, so into a running pane it steers or queues. Missing prerequisites do not refuse it; the panel's `setup` says what is missing.
- **Files.** A refusal carries a `code` (`workspaceNotFound`, `notFound`, `outsideWorkspace`, `notReadable`, `notDirectory`, `badPath`, `superseded`). Text is read up to 512 KiB, a thumbnail is at most 2,048 px on its long side and 512 KiB, a file reply is at most 768 KiB, and images are decoded one at a time, a newer preview from the same phone taking an older one's place in the queue.
- **Reply size.** A session reply may be 1 MiB − 32 KiB; over it the structure is shed first. A reply still over the limit is answered `413` rather than sent, because the relay closes the connection on a frame over 1 MiB.

Left as Windows has them, with no effect on the phone: `entries` answers without `before` (the phone always sends it), and revoking a device or regenerating the key unpairs every phone (below).

Implementation:

- `native/windows/MightyClaude.Core/Remote/RelayCrypto.cs`: X25519, HKDF-SHA256, directional counters, authenticated ChaCha20-Poly1305 frames. BouncyCastle.Cryptography provides the cryptographic primitives. The tests consume the same `native/contracts/relay-vectors.json` bytes as Mac/mobile.
- `MobileIdentity.cs`: stable host identity and device token hashes. A single atomically replaced `mobile-identity.json` stores the host private key, host token, pairing key, and device registry together. This differs from the separate Mac files so a failed write cannot commit a new pairing key while retaining old trusted tokens. The containing directory has a protected current-user Windows ACL; token values never enter the ordinary app snapshot or diagnostics.
- `MobileRelayHost.cs`: outbound control/data WebSockets, authenticated pairing, handshake and idle deadlines, reconnect, replay refusal, bounded concurrent connections and requests. The control socket is pinged every 20 s and closed when a ping goes unanswered for 10 s, so a half-open socket is replaced. `RelayLink.cs` holds the Mac's link rules: a network change redials about 1.5 s after the reports settle (at least 5 s apart, the gap doubling to 30 s while they keep coming), no network stops the dialling and says so until one returns, and a wake from sleep redials once the path has settled. The status carries why the last socket ended and the seconds until the next dial, which Settings shows under the state line. Pairing key regeneration or revoking a device removes all device credentials and disconnects every phone, matching the latest host policy. The UI states this before confirmation.
- `MobileUploads.cs`: device and pane ownership, exact sequential chunk sizes, bounded staging handles, and single-use claims spent only after accepted submission. Failed submissions release claims. Staging data is deleted on consumption or shutdown.
- `MobileDesktopRouter.cs`: m1 routing, ephemeral permission state, bounded JSON replies, read-only file access through `WorkspaceFiles`, and desktop callbacks. `MobileMighty.cs` (runs and blocks, permission card, transcript entries, settings options, the older phones' payloads), `MobileRevisions.cs` (per-pane revisions), `MobileWorkspaceFiles.cs` (listing, preview, refusal codes, the image preview slot) and `MobileStructure.cs` (`mighty.structure`: the shape, caps and per-pane cache of the Mac's `MobileStructure.swift`, built from `MightyStructure.Make`) hold the projections it sends.
- `MainWindow.MobileRemote.cs`: UI dispatcher boundary, QR/settings/device controls, queue/style-aware composer routing, status and execution graph projection. `MainWindow.MobileImages.cs` supplies bounded Windows image/PDF previews.

Protocol/authentication/ownership checks run cross-platform. Actual Windows capture, ACL behavior, QR rendering, clipboard, and phone integration must also be validated on a Windows machine; a macOS compiler cannot validate those native runtime behaviors. No real provider credentials or external relay are required by the tests. The encrypted relay test uses a local WebSocket fixture and generated test keys.

## Direct connection over Tailscale

When the phone and this PC are on the same Tailscale network, the phone opens its data socket straight to the PC (`ws://<address>:43139/ws?v=1`) instead of the relay; the handshake, encryption, auth and `/m1` tunnel are the relay path's, unchanged (`docs/relay.md`, "Tailscale 직접 연결" and "Windows 리스너"). Settings → Mobile remote has the switch (on by default), the port (43139, 1024–65535), a status line (the endpoints listened on, "Tailscale not found", or why binding failed) and the Windows Firewall rule's row.

- What counts as Tailscale: an up adapter that carries an fd7a:115c:a1e0::/48 address; its 100.64.0.0/10 and fd7a addresses are used. The adapter's name is not part of the rule (Windows lets the user rename it). The cases are `native/contracts/fixtures/tailscale-addresses.json`, shared with the Mac. The addresses are read again on every address change Windows reports and every 15 s.
- One `TcpListener` per address, never a wildcard; the app reads the WebSocket upgrade itself, so no administrator's URL ACL is needed.
- Limits as on the Mac: peers outside the two ranges reset at accept, 36 connections, 4 handshakes and 2 per address, a 10 s handshake, 5 failed auths per address per 60 s, the one-word `unauthorized` for every direct refusal, `direct-` ids; relay redials leave direct phones alone.
- Advertising: the `"direct"` capability, `auth_ok.direct`, `/m1/info` `direct` and the QR's `direct=`. No MagicDNS name.
- Firewall: the one place the app asks Windows to elevate, and only when the user clicks the firewall row's button or turns the remote or the direct switch off while the rule exists. The rule allows inbound TCP on the app's port from 100.64.0.0/10 and fd7a:115c:a1e0::/48, arriving at a local address in those same ranges, for `MightyClaude.exe` only, in every profile. **Add rule** runs `%SystemRoot%\System32\netsh.exe advfirewall firewall add rule name="Mighty Claude (Tailscale)" dir=in action=allow protocol=TCP localport=<port> localip=100.64.0.0/10,fd7a:115c:a1e0::/48 remoteip=100.64.0.0/10,fd7a:115c:a1e0::/48 program="<this exe>" profile=any` through UAC, or, when a rule by that name is already there, `set rule name="Mighty Claude (Tailscale)" new <the same body> enable=yes`, so rules never pile up; **Remove rule**, or turning the remote or the direct path off while the rule is there, runs `delete rule name="Mighty Claude (Tailscale)"`. Whether a rule by that name exists is read without elevation from `show rule`'s exit code (not whether its ports are current). When that read fails, the row says the rule is unknown and its button reads **Check again**, which reads again without asking for elevation. The button is **Remove rule** while the rule exists, **Add rule** while it does not, and absent when there is no port to open and no rule to remove. With the rule present, a changed port is not applied by itself: the hint beside the port says to remove the rule and add it again.
- Windows Defender Firewall's own alert: direct is on by default, so the first listen may bring up Windows' "Windows Defender Firewall has blocked some features of this app" alert, which the app does not control. **Allow access** adds Windows' own broad allow rule for the app. **Cancel** may add inbound block rules for `MightyClaude.exe`, and a block rule overrides the app's allow rule, so phones cannot connect directly until it is removed. The help (`docs/help/content/*/windows.md`) tells the user to allow it, or to remove the block rule in Windows Defender Firewall.
- Still to check on a real Windows PC: the UAC prompt and the rule; a phone connecting directly; Windows Defender Firewall's alert on the first listen, what **Allow access** and **Cancel** each leave in the inbound rules, and that a phone connects directly once a block rule is removed.

## Screen view and control

**Settings → Mobile remote → Screen view & control** grants each paired phone **None**, **View only**, or **Control**. New phones have no access. A control phone registers its P-256 public key, which requires matching-fingerprint confirmation on the PC; every control session then consumes a fresh, two-minute signed challenge. Legacy key-only clients cannot receive screen grants. Removing a key, downgrading a grant, rotating pairing identity, locking Windows, or focusing a password field ends the affected sharing session. The Mac ends its sessions on a lock or a secure input field too (`ScreenShareEngine.framesBlockedChanged`), so the phone shows the same hold on both. The in-app red stop control and physical **Ctrl+Alt+Esc** stop every session.

When the captured display disappears (unplugged, or Windows takes the stream away) the viewers are moved to the main display instead of being stopped, as on the Mac: capture restarts there, each phone is sent the displays there are now, and input that still names the missing display lands on the main one. A display that goes away while capture moves to it (undocking removes monitors one after another) is passed over once for the next. Only when no display is left, capture cannot start, or it keeps ending (more than three restarts within ten seconds) do the sessions end with `display-gone`; a frame that cannot be read or encoded ends them so too, without a restart, and a lock or password field that halted capture ends them at once with that reason. One capture serves every phone, so a phone that joins sees the display already captured. A display switch sends every phone a fresh offer (`iceRestart`) naming the new display.

- `ScreenShareHub.cs` owns local grants, enrollment, single-use challenges, one controller/two viewers, owner-bound signaling/input, local-input pauses, background/idle expiry, and teardown. Peer teardown precedes relay notification, including when a phone stops reading its relay socket.
- `WindowsScreenCapture.cs` uses Windows Graphics Capture and Win2D on the selected monitor, retaining the visible OS capture border. GPU crop/resize and bounded JPEG frames feed a bundled WebView2 page; frames never touch disk. Display IDs include virtual-desktop origins for multi-monitor input.
- `Assets/ScreenShare/screen.js` creates two send-only WebRTC video streams (`screen`, `overview`) and the reliable `screen-control` data channel used by the existing Android client. It negotiates H.264, applies individual phone resolution/fps/bitrate ceilings, and caps TURN paths to 2 Mbps. Relay-minted TURN credentials renew before their advertised TTL, with ICE restart.
- `WindowsRemoteInput.cs` observes local mouse/keyboard activity and protected-focus state without reading field contents. It injects only validated mouse actions, a closed shortcut vocabulary, and committed UTF-16 Unicode via `SendInput`. Windows UIPI still blocks elevated windows and secure desktops. Unknown or stale privacy state fails closed.
- `ScreenClipboard.cs` performs only explicitly requested text transfers. It bounds compressed and decoded data to 1 MiB, validates chunk ownership/order/metadata, and decodes zstd with a bounded window. Concealed clipboard formats never produce plaintext replies.
- `ScreenShareTapMarkerOverlay.cs` supplies the captured, click-through, non-activating half-second tap marker. The measurement scene runs in its own window, announces its phases over the data channel, and leaves other windows/documents untouched.

The current Windows path uses H.264 and SDR BGRA8 capture. Optional Mac cellular AV1/VP9 adaptation and HDR tone mapping are not established Windows parity. Hardware capture, Windows privacy/UIPI behavior, monitor changes, and Android end-to-end delivery still need Windows/device validation.

Verification has separate scopes:

- Core tests exercise shared encryption vectors, encrypted local WebSockets, grants/challenges/replay, revocation races, clipboard bounds and privacy teardown under a broken relay.
- `scripts/tests/test-windows-screen-webrtc.cjs` runs actual Chromium WebRTC with synthetic pixels and a local peer. It checks the two stream IDs, H.264, Korean/emoji data, decoded frames, per-phone resolution, and channel shutdown. Set `MIGHTY_PLAYWRIGHT_MODULE` to an installed `playwright-core` module and `MIGHTY_CHROMIUM_EXECUTABLE` if Chrome is not in the default macOS location. This does not capture a desktop or prove the Windows native backend.
- Windows UI smoke uses synthetic Win2D pixels and a native non-activating marker; it does not record the unattended runner's desktop.

The latest macOS implementation clears all device tokens when a pairing key is regenerated or a phone is revoked. Windows follows that source behavior. Some older relay documentation and translated helper text describe preserving other phones; those descriptions do not match the current host implementation.
