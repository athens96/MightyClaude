# macOS · Windows 실행기와 화면 차이 보완

2026-10-29에 `a16ed0b0`(0.4.46)을 기준으로 두 플랫폼의 CLI 실행, Mods 수신, 승인·재개, 하위 에이전트 그래프, 계획 카드와 실행 설정을 대조했다. Windows의 기본 화면은 `native/windows/web`의 WebView2 페이지이며, WinUI 화면은 대체 경로다. 과거 WinUI 화면의 기능 목록만으로 현재 Windows의 누락을 판단하지 않았다.

## 확인한 누락과 수정

| 영역 | Windows에서 확인한 문제 | 보완 |
| --- | --- | --- |
| Claude Mods | 실행기는 그래프를 요청하지만 수신기는 `agent.spawn`, `agent.complete`, `graph`를 거절했다. | 실행별 그래프 opt-in, 생명주기·필드 검증, 인증된 그래프 요청의 64 KiB 본문을 지원한다. 일반 이벤트의 16 KiB 한도는 유지한다. |
| 긴 실행 | 누적 4,096개 이벤트 이후 그 실행의 관측이 영구 차단됐다. | 누적 차단을 없애고 실행별 초당 120건 제한과 토큰 폐기를 유지한다. |
| 하위 에이전트 활동 | 파서에서 그래프로 도구 ID가 전달되지 않고 Mods 소유권 등록도 늦었다. | 소유권을 먼저 등록하고 원래 도구 ID로 자식 블록에 활동을 전달한다. |
| 승인 상태 | 늦게 도착한 도구 시작·대기 이벤트가 사용자의 승인 상태를 되돌렸다. | 표준 입력/출력 승인 채널의 상태를 우선하고 완료된 활동을 다시 열지 않는다. |
| 대화 재개 | 자식 세션의 Mods 이벤트가 루트 재개 ID를 덮어쓸 수 있었다. | 루트 CLI 출력만 재개 ID를 갱신한다. |
| 하위 에이전트 이미지 | 자식 이미지를 파서가 버리고 그래프의 정규화·저장 경로도 이미지 항목을 제외했다. | 자식 블록과 기존 갤러리에 이미지 참조를 전달하고, 크기 제한을 적용해 저장·복원한다. |
| 계획 기록 | 그래프에서 결정 결과·시각·수정 의견·잘림 안내가 빠지고 기록의 확대 보기가 없었다. | 기록과 그래프에 같은 계획 정보를 보여 주고 확대 문서 창을 제공한다. |
| 계획 수정 의견 | 16,384 UTF-8 바이트를 넘는 의견도 전송 단추가 켜져 있어 호스트에서만 거절됐다. | 입력 중 한도를 안내하고 전송을 막는다. 한글도 바이트 기준으로 계산한다. |
| 실행 설정 | 설정 창을 연 뒤 다른 경로에서 실행이 시작되면 적용되지 않은 설정도 저장된 것처럼 창이 닫혔다. | 실시간 실행 상태로 입력·적용을 잠그고, 호스트가 저장을 거절하면 창과 입력을 유지한다. |

주요 근거는 macOS의 `ModBridge.swift`, `CLIStreamParser.swift`, `ExecutionGraphTracker.swift`, `PlanApprovalCard.swift`와 Windows의 대응 Core 실행기 및 `web/src/cards`, `web/src/composer`, `web/src/mighty`다. 회귀 검사는 수신기 HTTP 경계뿐 아니라 파서·그래프·실행기 연결을 함께 확인한다.

재개 ID 처리는 Windows의 별도 개선이다. macOS 파서는 Mods로 ID를 바꾸지 않지만 `ProcessRunner.receiveMod`는 여전히 이를 전달하므로 두 플랫폼에 공통 위험이 있었다. 이번 변경은 Windows 실행기만 수정한다.

## 기존에 연결된 기능

기본 Windows 페이지에는 CLI·모델·추론 강도·권한 선택, 질문·계획·인증 복구 카드, Claude의 보낼 대상, 대기 요청·백그라운드 작업, 하위 에이전트와 이미지 갤러리가 이미 있다. 이번에는 이 화면들을 중복 구현하지 않고 누락된 데이터 전달과 상태 처리를 보완했다. 계정·모델 설정을 변경하거나 실제 모델을 호출하는 작업은 포함하지 않았다.

## 플랫폼 차이와 검증 한계

macOS의 AppKit/SwiftUI·로그인 셸·Keychain·Homebrew와 Windows의 WebView2/WinUI·ConPTY/PowerShell·CLI 자격 증명·winget은 각 운영체제에 맞게 유지한다. 단축키와 글꼴도 운영체제의 규칙을 따른다.

Windows의 WinUI 대체 화면은 보낼 대상 선택을 제공하지 않는다. 기본 웹 화면의 HTML 참조 말풍선은 아직 렌더링 대신 소스를 표시한다. 이처럼 실행기 보완과 별개인 화면 차이는 [웹 화면의 남은 차이](../native/windows/web/README.md#known-gaps)와 [화면 비교](../native/windows/web/VISUAL-PARITY.md)에 따로 기록되어 있다.

물리 키보드의 한글 입력기 전환, 창 활성화·복사/붙여넣기, 실제 CLI 계정 인증은 자동화된 가짜 CLI 검사로 증명할 수 없다. 이번 결과를 Windows의 모든 기능·기기에서 차이가 없다는 의미로 해석하지 않는다.

## 검증 결과

- 실제 Windows x64·ARM64에서 각각 Core 959개와 웹 Vitest 38개 파일·376개 테스트를 모두 통과했다. 실패·플랫폼별 건너뛰기는 0개다. 웹 TypeScript 검사도 통과했다.
- 이번 변경의 HTTP·실행기 신규 회귀 11개와 기존 사용량 회귀를 합쳐 집중 검사 12개 통과. 인증·실행 격리, 16/64 KiB 경계와 분할 전송, 토큰 폐기 중 업로드, 4,200개 이벤트, 지연 승인, 숫자 표기·순서, 사용량 중복 방지, 실제 가짜 CLI 실행과 이미지 저장·복원을 포함한다.
- WinUI C# 교차 컴파일 통과. 맥에서 생성할 수 없는 XAML의 `InitializeComponent` 한 건만 검사 스크립트의 예상 오류로 남았다.
- 번역·디자인 토큰·공백 검사 통과. 한글 길이 smoke의 고정 입력만 이유를 붙여 번역 검사에서 제외했다.
- 두 아키텍처 모두 WinUI 앱 빌드·ZIP/설치 프로그램 생성, 기본 웹 화면·WinUI 대체 화면, 설치·제거 검사에 통과했다.
- 실제 WebView2에서 계획 문서 확대·포커스 복원·기록 정보·한글 의견의 바이트 한도와 실행 설정의 잠금·해제·입력 유지·저장 거절을 확인했다. 좁은 창의 옵션 메뉴를 거치는 실행 설정 경로도 통과했다.
- 독립 검토에서 HTTP 수신기, 실행기와 이미지 저장, 웹 화면·호스트 변경에 차단 문제가 남지 않았다.

검증한 코드: `ecfa1b23`. [Windows x64·ARM64 CI 실행 40802433327](https://github.com/athens96/MightyClaude/actions/runs/40802433327)은 두 작업 모두 성공했다. 같은 실행의 `MightyClaude-native-windows-x64`·`MightyClaude-native-windows-arm64` 아티팩트에 ZIP과 설치 프로그램 및 SHA-256 파일이 있으며, 각 `web-smoke`·`smoke` 아티팩트에 화면 검사 결과와 스크린샷이 있다.
