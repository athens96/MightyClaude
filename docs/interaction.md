# 사용자 동작 목록

모든 입력은 **입력 → 처리 중 → 결과**로 보여야 한다. 이 문서는 맥·윈도우(웹 화면)·폰에서 사용자가 하는 동작 중 기다림이 생기는 것(호스트·CLI·디스크·네트워크를 거치는 것)을 모두 적고, 각 동작이 지금 무엇을 보여 주는지와 바뀔 모습을 둔다. 다음 계획들은 이 표를 기준으로 삼는다.

- 설계: [자연스러운 작동 (A 공통 구조 + B 요청 보내기)](superpowers/specs/2026-10-27-natural-submit-design.md)
- 조사: 2026-10-27, 세 앱의 소스 기준. 윈도우는 웹 화면(`native/windows/web`)만 본다. WinUI 대체 화면은 범위 밖이다.
- 공통 사례 파일: [`native/contracts/fixtures/pending.json`](../native/contracts/fixtures/pending.json), 모션 토큰은 [`design-tokens.json`](../native/contracts/fixtures/design-tokens.json)의 `motion`

**새 동작을 넣을 때는 이 표에 한 줄을 더하고, 처리 중 표시는 그 플랫폼의 공통 부품(아래 "플랫폼 부품")을 쓴다.**

## 공통 규칙

### 상태와 표시 규칙

입력 하나는 네 상태 중 하나다: `idle`(대기), `pending`(처리 중), `done`(완료), `failed`(실패, 메시지를 함께 가진다).

로딩을 보일지는 시작 시각·끝난 시각·지금 시각만으로 정한다(순수 함수 `PendingDisplay`).

- 시작 후 `pendingShowAfter`(150ms)가 지나도 안 끝났을 때만 보인다. 그 전에 끝나면(끝난 시각이 시작 + 150ms 이하) 한 번도 보이지 않는다.
- 보이기 시작했으면 시작 + 150 + `pendingMinVisible`(300ms)까지는 그 시각을 포함해 유지한다. 그 뒤로는 끝나는 즉시 숨긴다. 예: 200ms에 끝나면 450ms까지 보이고 451ms에 숨는다. 900ms에 끝나면 900ms에 바로 숨는다.
- `failed`: 끝난 시각(실패한 순간) 전까지는 처리 중이었으므로 위 규칙을 따른다. 실패한 순간부터는 오류가 바로 보이고, 보이던 로딩을 300ms를 기다리지 않고 바로 대신한다. 오류는 같은 자리에 남는다. 예: 100ms에 실패하면 50ms에는 아무것도 없고 100ms에 오류가 보인다. 400ms에 실패하면 150ms부터 로딩, 400ms부터 오류다.
- 사례의 `expectVisible`은 처리 중·실패 표시 자리가 보이는지를 뜻한다. 끝난 시각이 없는 `failed`는 잘못된 입력이며, 읽는 쪽은 끝난 시각을 지금으로 본다.
- "동작 줄이기"(Reduce Motion, 윈도우 애니메이션 효과 끄기, 폰 동작 줄이기)가 켜져 있으면 움직임만 없앤다. 보임·숨김 시각은 같다.

시각별 사례는 `pending.json`의 `display`에 있다. `node scripts/check-design-tokens.js --check`가 이 사례를 모션 토큰 값으로 다시 계산해 맞는지 본다.

### 모션 토큰

`design-tokens.json`의 `motion` 묶음이다. 맥 `DesignMetrics`, 윈도우 Core `DesignMetrics`, 웹 `theme/tokens`, 폰 `theme`이 같은 이름과 값을 둔다. 시간은 모두 ms 정수다.

| 이름 | 값 | 쓰임 |
|---|---|---|
| `quick` | 150 | 작은 상태 변화 (알약, 아이콘) |
| `standard` | 220 | 블록 등장·사라짐 |
| `scroll` | 280 | 스크롤·카메라 이동 |
| `easing` | `[0.2, 0, 0, 1]` | standard 이징 (cubic-bezier, x 값은 0~1) |
| `pendingShowAfter` | 150 | 로딩 표시 지연 |
| `pendingMinVisible` | 300 | 로딩 최소 표시 |
| `highlight` | 1200 | 강조가 남아 있는 시간 (대기열 줄 강조) |

### 보내기 응답

맥·윈도우 호스트의 보내기 응답(`POST /m1/sessions/{id}/submit`, 윈도우 웹 화면의 `send` 브리지)은 `{ accepted, entryId?, runId?, outcome? }`이다.

- `outcome`은 `started`, `queued`, `steered` 중 하나다. 없으면 `accepted`가 그 낱말일 때 그것을 쓴다(옛 호스트는 `{ protocol, accepted: "started" }`처럼 보낸다). `outcome`에 다른 값(예: `blocked`)이 오면 무시하고 `accepted`로 정한다. `accepted`가 불리언 `true`이면 받아들인 것이고 `outcome`은 비어 있을(null) 수 있다. 셋 다 아니면 받아들이지 않은 것이다.
- 새 호스트도 `accepted`에 같은 낱말을 넣어 옛 폰이 그대로 읽게 한다.
- `entryId`·`runId`는 비어 있지 않은 문자열일 때만 쓴다. 클라이언트는 이 id로 먼저 그려 둔 요청 블록과 호스트의 실제 항목을 맞춘다. id가 없는 옛 응답이면 보낸 글과 시각으로 맞춘다.
- `steered`는 요청이 실행 중인 Claude 프로세스에 새 턴으로 들어갔다는 뜻이다. 실행이 백그라운드 작업만 기다리고 있을 때 **다음 실행**이 대기열 첫 요청을 그렇게 넣고(맥 `AppStore.steersRunNext`, 윈도우 `SteerFirstQueuedInput`), 다이어그램에는 그 요청 아래 중간 요청으로 보인다. 옛 호스트와 새 호스트 모두 돌려줄 수 있다. 사용자가 실행 중인 턴에 직접 끼워 넣는 중간 요청은 없고, 실행 중에 보내면 대기열로 간다.

사례는 `pending.json`의 `submitResponses`에 있다.

### 화면 이동 규칙

내가 보낸 요청(이 입력창의 Enter, 대기열 요청이 실제로 실행될 때, 다음 실행, 선택된 ⌘Enter 자식 창)이 블록으로 생기는 순간, 보기와 위치에 상관없이 그 블록으로 `motion.scroll` 동안 이동한다. 동작 줄이기가 켜져 있으면 바로 이동한다.

| 보기 | 내 요청 | 다른 곳에서 온 요청·출력 |
|---|---|---|
| 기본 | 바닥으로 이동. 위를 읽고 있었어도 이동하고 선택 영역은 그대로 | 바닥 근처면 따라가고 아니면 그대로 |
| 흐름 | 따라가기 카메라로 이동(애니메이션) | 따라가기가 켜져 있으면 따라가고 아니면 그대로 |
| 파이프라인 | 지난 보드를 골라 두었으면 최신 보드로 되돌리고 새 요청 열로 이동 | 최신 보드 끝이면 따라가고, 지난 보드면 그대로(배지만) |
| 기록 | 마지막 묶음으로 이동 | 끝 근처면 따라가고 아니면 그대로 |

이동한 뒤의 출력은 지금의 따라가기 규칙을 따른다. 바닥 근처인지는 각 앱이 자기 기준으로 정한다(맥 36pt, 윈도우 32px, 흐름은 따라가기 카메라가 켜져 있는지, 기록·파이프라인은 최신 끝에 있는지). 사례 파일은 그 판단 결과만 받는다. 지난 파이프라인 보드를 보고 있을 때 다른 곳에서 온 갱신은 일부러 항상 그대로 둔다(지금처럼 배지만). 사례는 `pending.json`의 `scrollTargets`에 있다(`scroll`: `toRequest`·`follow`·`none`, `resetBoard`: 최신 보드로 되돌릴지).

### 플랫폼 부품

이번 계획에서 앱마다 하나씩 만든다. 새 단추·카드를 만들 때는 이 부품을 쓴다.

- **맥:** `PendingIndicator` 뷰와 `.pendingOverlay(state:)` 수정자. `MightyGraphActivityIndicator`의 막대 모양.
- **웹(윈도우):** `usePending()` 훅과 `<Pending>` 부품. 지금의 `.spinner`와 `.card-spinner`를 이것 하나로 합친다.
- **폰:** `usePending()` 훅과 `<Pending>` 부품. `Button busy`가 이 부품 위로 옮겨 간다.

문구: 처리 시작 전은 `graph.state.sending`(전송 중) 하나, 첫 실행 이벤트 뒤는 `graph.state.running`(실행 중)이다. 단계 이름은 보이지 않는다.

## 동작 표

**범위** 열의 뜻:

- **B**: 이번 계획에서 고친다.
- **A3**: 동작은 그대로 두고 표시만 공통 부품으로 바꾼다. 폰의 `Button busy`를 쓰는 동작은 모두 여기에 든다(모양과 표시 시각이 A1 규칙을 따른다).
- **C: 다음 계획**: 워크스페이스·창·보기 전환의 로딩과 속도. 다음 계획에서 다룬다.
- **그대로**: 지금 표시가 있고 이번에 바꾸지 않는다.
