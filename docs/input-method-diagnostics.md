# macOS 입력창과 한글 입력 진단

## 입력창 구조

메시지 입력창은 수명이 유지되는 기본 `NSTextView`를 사용합니다. macOS 입력기가 글자 조합과 대체 범위, 커서, 실행 취소를 처리합니다. 앱이 `insertText`의 한글을 직접 다시 조합하거나 입력 중 앱 활성화·첫 응답자를 자동으로 변경하지 않습니다. 과거의 직접 조합 설계는 `docs/hangul-fallback-composer.md`에 기록으로 남아 있습니다.

- **키 처리:** Enter·방향키·Tab·Escape는 입력기가 해석한 뒤 `NSTextViewDelegate.textView(_:doCommandBy:)`로 전달한 명령만 처리합니다. 입력기 전에 키를 가로채던 높이 측정기의 로컬 이벤트 모니터를 제거했습니다. 입력기가 후보 확정에 소비한 키는 전송하지 않습니다.
- **조합 직후 Enter:** 입력기가 마지막 글자의 조합을 끝내고 같은 Enter 이벤트에서 명시적인 줄바꿈 명령을 전달하면 바로 한 번 전송합니다. 키를 누르기 시작할 때 조합 중이었다는 이유만으로 이 명령을 막지 않습니다. 후보 확정만 하고 전송 명령을 전달하지 않은 이벤트, 아직 조합 중인 이벤트는 입력기에 맡깁니다. Shift+Enter 줄바꿈과 키 반복의 중복 전송 방지도 유지합니다.
- **줄바꿈 명령과 포커스:** `insertLineBreak:`도 Enter 명령 계열로 처리합니다. 네이티브 포커스 알림은 같은 `true` 값이 반복돼도 해당 창을 선택하며, 전송 여부는 현재 네이티브 입력 소유권으로 검증합니다. 지연된 활성 실행 창 상태 때문에 입력 중인 창의 Enter를 무시하지 않습니다.
- **초안 전달:** 네이티브 텍스트를 수정하는 도중 SwiftUI 바인딩을 쓰지 않습니다. 변경 알림을 모아 다음 메인 큐 실행에서 초안을 전달합니다. 전송·슬래시 완성 같은 명시적 동작은 네이티브 초안을 먼저 반영하므로 바로 앞에 입력한 글자가 빠지지 않습니다.
- **명시적 교체:** 새 초안을 지정하면 이전에 조합 종료를 기다리던 모델 변경을 취소합니다. 기존 코드에서 `조합 중 → 외부 초안 older → 명시적 교체 newer`가 `older`로 돌아가는 문제를 재현했고, 이 순서를 회귀 검사합니다.
- **편집기 연결:** 높이·자리표시자는 입력 컨트롤러가 소유한 정확한 편집기를 관찰합니다. 화면 좌표로 다른 입력창을 찾아 연결하지 않습니다. 편집기 제거 시 관찰과 예약된 초안 전달을 정리합니다.
- **복귀 후 첫 클릭:** 편집 가능한 메시지 입력창은 다른 창에서 돌아오는 첫 클릭도 받습니다. 우선 기본 AppKit 마우스 처리를 따릅니다. 클릭한 입력란이 포커스를 얻지 못한 경우에는 아래의 연결 확인 경로가 실제 앱·창 활성화를 확인한 뒤 정확히 그 입력란에 한 번만 포커스를 요청합니다.
- **입력 세션 복구:** `InputSessionRecoveryCoordinator`가 마지막으로 포커스를 가졌던 편집기와 창을 약하게 기억합니다. 키 윈도가 없어도 같은 창의 현재 첫 응답자로 남아 있는 보이는 편집기를 찾을 수 있습니다. 재연결은 사용자가 요청한 대상에만 적용하며, 활성화 요청과 실제 활성화 확인을 분리합니다.
- **일반 입력란 복구:** 검색창·이름 입력란·콤보박스는 창이 공유하는 필드 편집기를 사용합니다. 편집 시작과 창의 키 상태 해제 알림에서 정확한 현재 편집기와 원래 `NSControl`을 약하게 기억합니다. 클릭만 하고 아직 글자를 입력하지 않은 필드도 대상에 포함됩니다. 복구는 그 컨트롤을 통해 편집을 다시 시작한 뒤 현재 편집기를 얻습니다. 편집 종료 콜백이 바꾼 값을 덮어쓰지 않으며 선택 범위를 현재 문자열 길이 안에서 복원합니다. 소유자나 포커스가 바뀌면 취소합니다.
- **탭 이동과 키 입력:** 탭의 마우스 누름·이동·놓기는 각 AppKit 이벤트에서 처리하고 즉시 반환합니다. 별도 `nextEvent` 루프에서 키보드 이벤트를 가져가지 않습니다. 제스처 중에도 문자와 복사 단축키는 정상 전달하며, 앱·창·Space 변경, 표시 대상 해제, 새로운 클릭, 놓기 이벤트 유실 때 추적을 취소합니다.
- **그래프와 창 활성화:** 그래프의 로컬 이벤트 모니터는 앱과 그래프 창이 실제 키 입력 대상인 경우에만 제스처를 처리합니다. 비활성 창으로 돌아오는 클릭은 기본 창 처리에 전달하며, 활성 상태를 잃은 기존 드래그는 취소합니다.
- **터미널 포커스:** 터미널의 늦게 도착한 포커스 알림으로 이전 실행 창을 다시 선택하지 않습니다. 포커스 해제·표시 소유권 변경·표면 해제·폐기 때 예약을 취소하고, 실행 시에도 앱·키 윈도·첫 응답자·표시 상태가 같은지 확인합니다.

붙여넣기 첨부, 여러 줄 입력, Enter 전송, ⌘Enter 즉시 전달, Shift+Enter 줄바꿈, 슬래시 완성은 기존 기능을 유지합니다. 실제 입력 소스의 조합 과정과 단축키 해석은 macOS 입력기를 통해 추가 확인해야 합니다.

## 한글 모드의 복사·붙여넣기

`ApplicationCopyRouter`는 ⌘C·⌘V를 현재 창의 실제 첫 응답자에게 한 번 전달합니다. 영문 단축키 문자를 우선하고, 한글 문자로 전달된 이벤트에는 물리 키 위치를 보완적으로 사용합니다. `charactersIgnoringModifiers`도 입력 배열의 문자를 돌려주는 속성이므로 항상 영문이 된다고 가정하지 않습니다. [Apple NSEvent 문서](https://developer.apple.com/documentation/appkit/nsevent/charactersignoringmodifiers)

메시지 입력창과 일반 필드 편집기는 기본 `copy:`·`paste:` 동작을 사용합니다. 메시지 입력창의 이미지·파일 첨부 처리와 터미널의 `paste_from_clipboard` 경로도 유지합니다. 복사·붙여넣기 처리가 입력기를 강제로 바꾸거나 조합 글자를 직접 다시 만들지 않습니다. 읽기 전용 결과 블록의 붙여넣기를 다른 입력란으로 보내지 않습니다.

단축키를 처리하기 전에 동일 창의 이전 클릭 복구 요청을 취소합니다. 복사는 텍스트나 선택 영역을 변경하지 않을 수 있으므로, 내용 변경 알림만으로 오래된 포커스 요청을 취소할 수는 없습니다. 다른 창·가려진 입력란·다른 모달 창으로는 전달하지 않습니다.

## 확인된 문제와 남은 범위

2026-09-21 06:52:58 UTC 진단에서 입력창은 첫 응답자로 키를 받고 있었지만 앱은 비활성, 키 윈도는 없음, 현재 입력 컨텍스트도 없음으로 기록됐습니다. 선택된 입력 소스는 Apple 두벌식이며 보안 입력은 꺼져 있었습니다. 최근 이벤트에는 자동 활성화 시도가 반복됐지만 입력 컨텍스트 복구는 기록되지 않았습니다.

이 기록은 입력창 내부의 오래된 초안 덮어쓰기와 별개로 앱 활성 상태와 입력 컨텍스트를 확인해야 함을 보여줍니다. 각 과거 기록 시점의 화면 잠금 여부는 확인되지 않아 기록만으로 활성화 결함을 확정하지 않습니다. 입력창을 단순화했다고 macOS 활성화 장애까지 해결됐다고 결론 내리지 않습니다. 이전 조사에서도 앱 번들 교체 없이 장시간 사용 중 재발한 사례가 있어 번들 교체를 단일 원인으로 확정하지 않습니다.

같은 날 09:04:34·09:05:34 UTC에도 새 입력창을 설치한 앱에서 비활성·키 윈도 없음·현재 입력 컨텍스트 없음이 다시 기록됐습니다. 이때 선택된 소스는 US였습니다. 기존 복구 메뉴는 키 윈도에서만 대상을 찾아 이 상태에서 아무 작업도 하지 않았고, ASCII 또는 무삽입 경로는 복구 안내를 올리지 않았습니다. 이 두 공백과 활성화 확인 전 포커스를 바꾸던 순서를 수정했습니다. 앱이 처음 비활성 상태로 남게 되는 계기까지 확정된 것은 아닙니다.

추가 조사에서 탭의 기존 중첩 마우스 추적 루프가 일반 키·⌘C·다음 클릭을 정상 전달하지 않는 것을 재현했습니다. 또한 실제 `NSTextField`에서 기존 재연결이 공유 편집기를 분리한 뒤 복구를 취소하여 편집 상태를 끝내는 것을 재현했습니다. 두 경로를 각각 이벤트별 제스처 처리와 입력란 소유자 기반 복구로 변경했습니다. 이 결함의 재현은 과거 macOS 활성화 장애 전체가 같은 원인임을 증명하지 않습니다.

## 자동 진단

`InputMethodMonitor`는 입력 콜백과 상태를 관찰합니다. 입력 내용을 바꾸거나 자동으로 포커스를 옮기지 않습니다.

1. 한국어 입력 소스에서 자음·모음 자모가 조합되지 않은 증상이 반복되면 기존 증상 진단과 수동 재연결 안내를 기록합니다. 두벌식의 첫 자모 삽입 자체는 정상이며, 후속 `insertText(_:replacementRange:)`가 앞 글자를 바꾸는 경로도 보존합니다.
2. 같은 입력창에 키 이벤트가 연속으로 들어오는데 앱·창이 비활성이거나 입력 컨텍스트가 없거나 일치하지 않으면 상태 진단을 저장하고 복구 안내를 표시합니다. 이 경로는 영어로 입력되거나 문자가 전혀 삽입되지 않아도 동작합니다. 입력 문자열과 최근 입력 이벤트는 이 자동 상태 파일에 저장하지 않습니다. 키 처리 후 비동기로 기록하며, 60초 안에 반복 저장하지 않습니다. 이 관찰만으로 물리 키보드 이벤트임을 보증하지 않습니다.

진단은 `<상태 저장 위치>/diagnostics/ime-<시각>-<식별자>.json`에 저장합니다. 파일 권한은 0600입니다. 상태 진단에는 앱 활성 상태·입력 소스·키 윈도·컨텍스트 일치 여부와 최대 60개의 활성화·키 윈도·입력 소스 변경 이력이 들어갑니다. 이 이력은 키 문자·초안·다른 앱 이름을 포함하지 않습니다. 자소 증상 및 수동 진단에는 기존처럼 최근 입력 콜백과 초안 끝부분이 포함될 수 있으므로 외부에 공유하기 전에 확인합니다.

## 수동 복구와 확인

문제가 난 입력창에 포커스를 둔 채 **워크스페이스 → 입력기 진단 저장**으로 복구 전 상태를 남길 수 있습니다. 키 윈도가 없을 때도 유효한 마지막 편집기를 대상으로 사용합니다.

**입력기 다시 연결**은 사용자가 명시적으로 실행한 경우에만 동작합니다. 앱 활성화가 필요한 경우 한 번 요청한 뒤 실제 앱·대상 창의 활성화를 기다립니다. 그 전에 초안·조합·선택 영역이나 첫 응답자를 바꾸지 않습니다. 대상이 활성화되면 보이는 조합 글자를 확정하고 선택 영역을 보존하며 일반 첫 응답자 경로로 재연결합니다. 입력 컨텍스트가 실제로 일치하는지 확인한 뒤 연결 상태를 표시하며, 시간 초과·대상 변경·포커스 변경은 실패 또는 취소로 구분합니다. 단순히 요청을 보냈다는 이유로 성공으로 표시하지 않습니다.

대기 중 다른 편집기나 창을 선택하거나 입력창이 숨겨지거나 제거되면 이전 요청은 더 이상 그 편집기를 조작하지 않습니다. `NSTextInputContext.activate/deactivate` 직접 호출, ABC↔한글 자동 전환, 키 이벤트 재전송은 사용하지 않습니다. 컨텍스트 연결 확인은 실제 한글 문장 조합 검증을 대신하지 않습니다.

## 클릭·앱 복귀 시 연결 확인

같은 `InputSessionRecoveryCoordinator`가 사용자의 입력란 클릭과 자기 앱으로 돌아온 알림도 처리합니다. 정상 네이티브 이벤트가 끝난 뒤 연결 상태를 확인하며, 이미 정상인 입력란은 재설정하지 않습니다. 다른 앱이 전면이면 활성화를 요청하지 않습니다. 수동 복구와 별개의 복구 루프를 만들지 않습니다.

자동 경로는 조합 중인 글자를 확정하거나 버리지 않습니다. 현재 조합·키 입력 처리가 끝나지 않았거나 대상·창·포커스가 바뀌면 기다리거나 취소합니다. 앱과 키 윈도우 활성화는 실제 상태를 확인하며, 필요할 때만 네이티브 첫 응답자 경로로 한 번 재연결합니다. 앱 복귀만으로 새로운 입력란을 선택하지 않습니다.

클릭 복구를 기다리는 동안 기존 입력란에서 새로운 키 입력·선택 변경·내용 변경이 발생하면 이전 클릭 요청을 취소합니다. 이 관찰은 입력 내용을 저장하지 않고 키 이벤트를 그대로 전달합니다. 같은 공유 필드 편집기가 이미 클릭한 입력란으로 이동한 경우에는 오래된 포커스로 오인하지 않습니다.

빌드는 실행 중인 앱의 LaunchServices 등록을 변경하지 않습니다. 앱 교체와 등록 변경은 설치기가 앱의 정상 종료를 확인한 뒤 수행합니다. 같은 설치 대상에는 하나의 설치기만 접근할 수 있고, 백업은 충돌하지 않는 고유 폴더에 저장합니다. 대기 중인 설치기를 취소해도 복사를 계속하는 자식 설치기를 남기지 않습니다.

실제 기기에서는 다음을 확인합니다.

- 두벌식 문장 입력 도중 다른 앱으로 갔다 돌아와 계속 입력하고, 여러 에이전트 입력창 사이를 이동합니다.
- 일반 한글 문장 마지막에서 Enter 한 번으로 전송되는지, ⌘Enter와 Shift+Enter가 각각 전송·줄바꿈으로 동작하는지 확인합니다. 별도의 후보 선택 창에서 확정한 경우에는 의도하지 않은 메시지 전송이 없는지도 확인합니다.
- 한자 후보 선택, 선택 영역 교체, 붙여넣기, 실행 취소·다시 실행, 슬래시 완성 후 이어 쓰기를 확인합니다.
- 한글 모드에서 블록과 터미널의 선택을 ⌘C로 복사합니다. 이 복사 경로는 메시지 입력창의 새 조합 처리와 독립적입니다.

`ComposerInputTransactionDiagnostics`는 실제 편집기·코디네이터의 초안 전달과 명령 처리를, `ComposerPresentationDiagnostics`는 앱 안에서 자리표시자·높이·편집기 소유권을 검사합니다. 합성 콜백과 명령 검사는 실제 macOS 한글 입력기의 장시간 재발 여부를 대신하지 않습니다.

화면 전환 회귀 검사는 `scripts/tests/test_pane_dock_input.py`, 복구 검사는 `scripts/tests/test_input_session_recovery.py`로 실행합니다. 보이지 않는 AppKit 테스트 창을 사용하며 활성 창·키보드 입력 소스·시스템 클립보드를 변경하지 않습니다. AppKit 검사는 WindowServer 접근이 필요합니다. 별도 번들·임시 프로필을 사용하는 레이아웃 통합 검사는 `artifacts/input-transitions/run-layout-check.py`와 조사 보고서에 기록합니다.
