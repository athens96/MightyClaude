# 백그라운드 작업 알림을 새 다이어그램으로

2026-10-28 · 사용자 요청: 알림으로 처리하는 루틴 개선. 흐름에서는 진행 중인 백그라운드 작업을 입력창 위 작업 줄에 두고, 끝나면 새 다이어그램을 만든다. 기록과 파이프라인에서는 새 알림을 다음 줄에 둔다.

정한 것:
- 다이어그램은 Claude 답 하나당 하나.
- 진행 중 표시는 작업 줄에서 펼쳐 본다.
- 원래 결과의 "작업 알림 이후" 절은 뺀다.
- 맥, 윈도우, 폰 모두 적용한다.
- 방식 A: 흐름 추적기가 알림 턴을 새 실행으로 기록한다.

## 알림이 올 작업은 미리 안다
Claude가 다음 둘을 실행하면 나중에 `<task-notification>`이 온다.
- `run_in_background`로 띄운 Agent(하위 에이전트)
- `run_in_background`로 띄운 Bash(명령)

흐름 추적기는 이 블록에 이미 `background: true`를 단다(0.4.45). 입력창 위 작업 줄은 CLI의 `system` task 이벤트로 같은 작업을 안다.

## 지금 동작
- 백그라운드 블록이 그 작업을 띄운 요청의 다이어그램 안에 생긴다.
- 작업이 끝나면 그 다이어그램에 "작업 알림" steer 블록이 붙는다.
- 알림 턴의 답은 원래 요청 결과 끝에 `작업 알림 이후` 절로 붙는다.

## 바뀌는 동작

### 1. 진행 중: 입력창 위 작업 줄
- 백그라운드 블록(`background == true`인 agent와 task)은 **원래 요청의 흐름, 기록, 파이프라인에 그리지 않는다.**
  - 데이터는 그대로 실행에 남는다. 화면만 거른다.
  - 폰으로 보내는 블록과 구조에서도 뺀다.
- 입력창 위 "백그라운드 작업" 줄(맥 `BackgroundWorkStrip`, 윈도우 WinUI와 웹 카드)이 진행 중인 작업을 보인다.
  - 각 행: 종류 이름(0.4.45), 이름, 경과, 출력 마지막 한 줄.
  - **펼친 행:** 실행한 명령, 그리고 출력 마지막 줄들(최대 6줄, 0.4.45의 꼬리 규칙). 하위 에이전트는 설명(프롬프트 첫 줄)을 보인다.
  - 작업 줄의 행과 흐름 블록은 `toolUseId`로 잇는다(0.4.45와 같다).
- 폰에는 작업 줄이 없다. 흐름(마이티) 보기 위쪽에 "백그라운드 작업 N개" 접힌 한 줄을 둔다. 펼치면 같은 행들이 보인다.
  - 호스트는 세션 상세에 선택 필드 `backgroundWork?: [{ id, kind: "agent"|"run", title, status, startedAt, command?, outputTail? }]`를 싣는다.
  - 진행 중인 것만 싣는다. 출력 파일 경로는 싣지 않는다.

### 2. 완료: 새 실행(다이어그램)
- **새 실행을 여는 시점:** 요청 자신의 턴이 아닌, 최상위 `<task-notification>`이 연 턴이 시작될 때 흐름 추적기가 새 실행(MightyGraphRun)을 연다. "Claude 답 하나당 하나"이므로 그 턴에 함께 들어온 알림은 모두 같은 실행에 묶는다.
- **새 실행의 내용**
  - **main 블록**
    - 제목: `graph.background.noticeRun` "백그라운드 작업 완료".
    - 입력: 끝난 작업 이름들. 예: "빌드 실행 · 완료, 테스트 에이전트 · 실패".
    - 결과: 그 턴에서 Claude가 답한 글 전체.
  - **자식 블록:** 이번 턴이 다룬 끝난 백그라운드 작업마다 하나다. 원래 블록의 사본이다.
    - 종류: agent / task
    - 제목
    - 명령 또는 프롬프트
    - 상태
    - 알림 요약
    - 마지막 출력 꼬리
    - 하위 에이전트이면 보고(hand-back)
  - 원래 블록과는 `sourceBlockId`로 잇는다.
- **다른 요청 중에 흡수된 알림:** 알림이 다른 요청이 실행 중일 때 들어와 그 요청 턴 안에서 처리되면(`<system-reminder>` 안 등), 알림 턴이 따로 없다. 이때도 새 실행을 만들되 결과는 비워 둔다. 끝난 작업 블록만 있고 main은 완료 상태다. 그 요청의 답은 그 요청의 결과로 남는다.
- **원래 요청에서 빼는 것**
  - 알림 턴의 답을 원래 main 결과에 `작업 알림 이후` 절로 붙이지 않는다(`graph.result.afterTaskNotice` 경로).
  - 원래 다이어그램에 "작업 알림" steer 블록(`addNotice`)을 만들지 않는다.
  - 위임 알림(`graph.result.afterNotice`, 위임 notice)과 사용자의 다음 실행 steer는 이번 범위가 아니라 그대로 둔다.
- **세지 않는다:** 새 실행은 사용자가 보낸 요청이 아니다. 사용자 요청 번호, 펫, 완료 알림 횟수에 넣지 않는다. 다만 새 실행이 생겼다는 데스크톱/폰 알림(완료 알림)은 지금 알림 턴이 끝날 때 나가는 것과 같이 한 번 나간다.

### 3. 기록과 파이프라인
- 새 실행은 실제 실행이 하나 더 생긴 것이라 지금 구조를 그대로 따른다.
  - **기록**(타임라인과 대화): 맨 아래 다음 줄에 "백그라운드 작업 완료" 묶음으로 붙는다.
  - **파이프라인:** 맨 끝에 새 보드 또는 행으로 붙는다.
- 제목 앞에 작은 표시를 둔다. 기존 task 아이콘(터미널)을 다시 쓴다.

### 4. 지난 기록 다시 읽기
`SessionHistory`가 Claude 기록을 다시 읽을 때도 같은 흐름 추적기를 지나므로 같은 새 실행이 생긴다. 다른 경로가 있으면 맞춘다.

## 문구
locale 키를 `locales/{ko,en,zh,ja}.json`과 사본에 넣는다.
- `graph.background.noticeRun` "백그라운드 작업 완료"
- `graph.background.stripTitle` "백그라운드 작업 {count}개"(폰 접힌 줄). 같은 뜻의 기존 키가 있으면 그것을 쓴다.

## 범위
- Claude 창만이다. 맥(MightyCore 흐름 추적기, MightyGraph, 앱 화면, 폰 변환), 윈도우(Core, 호스트, 웹 화면), 폰(타입, 마이티 보기, 구조)을 바꾼다.
- `docs/mobile-remote.md`에 `backgroundWork`와 새 실행을 적는다.
- 도움말 4개 언어에 백그라운드 작업 절을 고쳐 적는다.
- 고정된 스타일 엔진(`MightyCore/Styles/**`)은 건드리지 않는다.

## 테스트
- `native/contracts/fixtures/agent-notices.json`에 사례를 더한다. 맥과 윈도우가 같은 파일을 읽는다.
  - 명령 알림 하나 → 새 실행 1개. 자식 1개, main 결과가 답이다.
  - 한 메시지에 알림 둘 → 새 실행 1개, 자식 2개.
  - 하위 에이전트 보고와 알림 → 자식의 결과가 보고다.
  - 다른 요청 중에 흡수된 알림 → 결과가 빈 새 실행이 생기고, 원래 요청 결과는 그대로다.
  - 원래 요청 main 결과에 `작업 알림 이후` 절이 없고, 작업 알림 steer 블록도 없다.
  - 원래 실행의 background 블록은 데이터에 남지만 화면용 목록에서는 빠진다. 이를 거르는 순수 함수를 테스트한다.
- 폰: `backgroundWork` 파싱, 새 실행 그리기 규칙(jest).
- 웹: 백그라운드 블록 거르기, 새 실행 제목(vitest).
