# 자연스러운 작동 (A 공통 구조 + B 요청 보내기)

2026-10-27 · 사용자 결정 (brainstorming)

## 목표
모든 입력은 **입력 → 처리 중 → 결과**로 보여야 한다. 이번 범위는 두 가지다.
- **A. 공통 구조.** 상태 모델, 로딩 표시 규칙, 모션 토큰, 동작 목록 문서. 맥·윈도우(웹 화면)·폰이 공유한다.
- **B. 요청 보내기.** Enter를 누른 순간부터 결과까지가 자연스럽게 이어지게 한다.

C(워크스페이스·창·보기 전환의 로딩과 속도)는 다음 계획에서 다룬다.

## 사용자가 정한 것
- 순서: A+B 먼저, C는 다음.
- 내가 Enter로 보낸 요청은 어느 보기든, 어느 위치든 **항상 그 요청으로 이동**한다. 파이프라인은 최신 보드로 돌아간다.
- 대기열에 들어간 요청은 **입력창 위 대기열 줄만 강조**한다. 대화나 다이어그램에 블록을 만들지 않는다. 실제로 실행될 때 블록이 생기고 그리로 이동한다.
- 처리 시작 전 표시는 **단순 로딩**이다. 단계 이름 없이 "전송 중" 하나만 보이고, 첫 응답이 오면 "실행 중"으로 바뀐다.

## A. 공통 구조

### A1. 상태 모델 `PendingState`
모든 입력은 다음 네 상태 중 하나다.
- `idle`: 대기
- `pending`: 처리 중
- `done`: 완료
- `failed`: 실패, 메시지를 함께 가진다

표시 규칙 `PendingDisplay`는 순수 함수다. 시작 시각, 끝난 시각, 지금 시각을 받아 로딩을 보일지 정한다.
- 시작 후 `showAfter`(150ms)가 지나도 안 끝났을 때만 보인다.
- 보이기 시작했으면 최소 `minVisible`(300ms)는 유지한다. 그 전에 끝나도 그때까지는 보인다.
- `failed`는 즉시 보인다. 오류는 같은 자리에 둔다.
- "동작 줄이기"가 켜져 있으면 움직임만 없앤다. 보임과 숨김 규칙은 같다.

### A2. 모션 토큰
`native/contracts/fixtures/design-tokens.json`에 `motion` 묶음을 더한다.

| 이름 | 값 | 쓰임 |
|---|---|---|
| `quick` | 150 | 작은 상태 변화 (알약, 아이콘) |
| `standard` | 220 | 블록 등장·사라짐 |
| `scroll` | 280 | 스크롤·카메라 이동 |
| `easing` | `[0.2, 0, 0, 1]` | standard 이징 (cubic-bezier) |
| `pendingShowAfter` | 150 | A1 표시 지연 |
| `pendingMinVisible` | 300 | A1 최소 표시 |
| `highlight` | 1200 | 강조가 남아 있는 시간 (대기열 줄 강조) |

맥 `DesignMetrics`, 윈도우 Core `DesignMetrics`, 웹 `theme/tokens`, 폰 `theme`이 이 값을 그대로 두고, 기존 토큰 동등성 검사에 포함한다.

### A3. 플랫폼 부품 (앱마다 하나씩)
- **맥:** `PendingIndicator` 뷰와 `.pendingOverlay(state:)` 수정자. 기존 `MightyGraphActivityIndicator`의 막대 모양을 쓰고 A1을 따른다.
- **웹(윈도우):** `usePending()` 훅과 `<Pending>` 부품. 기존 `.spinner`와 `.card-spinner` 두 벌을 하나로 합친다.
- **폰:** `usePending()` 훅과 `<Pending>` 부품. 기존 `Button busy`를 이 부품 위로 옮긴다.
- 새 버튼이나 카드를 만들 때는 이 부품을 쓰는 것이 규칙이다.

### A4. 동작 목록 문서
`docs/interaction.md`에 모든 사용자 동작을 표로 둔다. 열은 다음과 같다.
- 동작
- 플랫폼별 진입점
- 처리 중 표시
- 실패 표시
- 화면 이동 규칙

이번 계획에서 고치지 않는 항목도 현재 상태와 함께 적는다. C를 포함한 다음 계획들이 이 표를 기준으로 삼는다. 새 기능을 넣을 때는 이 표에 한 줄을 추가하는 것이 규칙이다. `CLAUDE.md`나 개발 문서의 기여 규칙에도 한 줄 적는다.

## B. 요청 보내기

### B1. Enter 직후 (세 앱 공통)
같은 화면 틱에서 다음을 한다.
1. 입력창을 비운다.
2. 요청 블록을 만든다. 기본 보기에서는 말풍선, 흐름·파이프라인·기록에서는 요청 블록이다. 상태는 `pending`이다.
3. A1 규칙으로 "전송 중" 로딩을 띄운다. 블록 안에 막대 모양과 "전송 중" 글자를 보인다.

첫 CLI 이벤트(실행 시작)가 오면 블록은 "실행 중"이 되고, 지금 쓰는 실행 표시로 넘어간다.

실패하면(시작 실패, 호스트 거절, 네트워크) 다음과 같다.
- 블록은 `failed`가 되어 오류 메시지를 보인다.
- 입력창이 그사이 비어 있고 바뀌지 않았으면 원래 글을 되돌린다. 맥의 지금 규칙을 따른다.

### B2. 화면 이동 (세 앱, 네 보기 공통)
내가 보낸 요청이 블록으로 생기는 순간, 보기와 위치에 상관없이 그 블록으로 이동한다. 시간은 `motion.scroll`(280ms)이고, 동작 줄이기가 켜져 있으면 즉시 이동한다.

| 보기 | 이동 방식 |
|---|---|
| 기본 | 바닥으로 이동한다. 위를 읽고 있었어도 이동하며, 선택 영역은 유지한다. |
| 흐름 | 지금처럼 따라가기 카메라를 쓴다. 지금은 즉시 이동하는데 애니메이션을 더한다. |
| 파이프라인 | 사용자가 고른 지난 보드를 최신 보드로 되돌리고, 새 요청 열로 이동한다. |
| 기록 | 마지막 묶음으로 이동한다. 지금 `LazyVStack` 때문에 덜 가는 문제를 함께 고친다. |

이동한 뒤 출력은 지금의 따라가기 규칙을 그대로 따른다.

같은 규칙을 쓰는 경우:
- 대기열 요청이 실제로 실행될 때
- 다음 실행(중간 요청)
- ⌘Enter 워크트리 실행: 자식 창이 선택된 경우만. 선택되지 않으면 사이드바 자식 행이 A1 로딩을 보인다.

### B3. 대기열 강조
바쁠 때 Enter를 누르면 다음과 같다.
- 입력창은 바로 비운다.
- 입력창 위 대기열 줄이 `motion.highlight` 동안 강조색으로 깜빡인다.
- 새로 추가된 항목은 `standard` 등장 효과로 나타난다.

대화나 다이어그램에는 블록을 만들지 않는다.

### B4. 앱별 작업
- **맥**
  - 이미 바로 블록이 생긴다. `MightyGraphRun.status`에 쓰지 않던 `"starting"`을 실제로 써서 첫 이벤트 전까지 "전송 중"으로 보인다. 대화 말풍선에도 같은 표시를 단다.
  - 화면 이동은 B2에 맞춘다(기본·파이프라인·기록). 대기열 강조를 더한다.
  - 중지 중 표시는 A3 부품으로 바꾼다. `stopping` 상태는 지금 창이 다시 그려지면 사라지므로 스토어로 옮긴다.
- **윈도우(웹 + 호스트)**
  - 페이지가 Enter 순간 직접 블록을 만든다(낙관적). 클라이언트 id를 붙여 `send`를 보내고, 호스트 delta의 실제 항목이 오면 그 블록과 맞춰 바꾼다. 맞추는 기준은 send 응답이 주는 항목·실행 id다. 이를 위해 호스트 응답에 id를 더한다.
  - 입력창은 Enter 순간 비운다.
  - 흐름 보기는 1초 루프를 기다리지 않는다. 시작할 때 `graph_run`을 바로 내보낸다.
  - 실행 시작부터 첫 출력 사이에는 "실행 중" 행을 보인다. 지금 버려지는 `activities`를 쓴다.
  - 카드 답변(권한 카드 포함)은 처리 중 잠그고 A3 로딩을 보인다.
  - 보기 모드 단추는 낙관적으로 바뀐다.
  - 글자를 칠 때마다 호스트로 보내는 초안 저장(`updateDraft`)은 묶어서 보낸다(디바운스 300ms). 전송 순간에는 즉시 보낸다.
- **폰**
  - Enter 순간 입력창을 비우고, 보낸 글로 요청 말풍선·블록을 만든다(낙관적).
  - 호스트의 submit 응답에 항목 id를 더해 맞춘다. 응답이 없는 옛 호스트에서는 글과 시각으로 맞춘다.
  - 화면 이동은 B2를 따른다. 지금 `followNewest`가 항목이 오기 전에 실행되는 문제를 고친다.
  - 중지·슬래시 명령 등 표시 없는 동작에는 A3 로딩을 단다.

### B5. 호스트 응답에 id 추가 (윈도우·폰 공통 계약)
- Mac·Windows 호스트의 submit 응답(`/m1/sessions/{id}/submit`과 윈도우 웹 `send` 브리지)이 `{ accepted, entryId?, runId?, outcome }`을 돌려준다.
- `outcome`은 `started`, `queued`, `steered` 중 하나다.
- 옛 응답(필드 없음)도 그대로 받아들인다.
- `docs/relay.md`나 모바일 원격 계약 문서에 적고, 공통 사례 파일로 맞춘다.

## 확인
- **공통 사례 `native/contracts/fixtures/pending.json`:** A1 표시 규칙의 시각별 사례와 B5 응답 모양 사례. 맥 MightyCore, 윈도우 Core, 웹 vitest, 폰 jest가 같은 파일을 읽는다.
- **디자인 토큰 동등성 검사:** `motion` 묶음을 포함한다.
- **화면 이동 규칙:** 순수 함수로 뺀 부분(이동할 목표, 파이프라인 보드 되돌리기)을 각 플랫폼에서 테스트한다.
- **윈도우 성능 시나리오:** `scripts/perf-scenario.ps1`에 "전송 → 블록 보임" 시간을 추가한다. 목표는 한 프레임(≤50ms)이다.
- 빌드·테스트는 사용자가 요청할 때만 돌린다. 텍스트 검사(locales, design-tokens, help, style-freeze)는 돌린다.
